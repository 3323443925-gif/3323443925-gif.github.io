01文档说明

1.1 目的

定义「个人网站」首个可上线版本的产品范围、用户场景、功能行为与内容规则，使站长（内容作者）与实现方对“做什么、不做什么、做到什么程度”达成一致。

1.2 读者

站长本人、参与实现的前端 / 设计协作者、后续维护者。

1.3 不包含

技术架构、代码实现、视觉稿与运营计划。第 10 章的技术选型建议为附录，仅作参考，不构成需求约束。

1.4 术语

术语定义
内容条目站点上可被单独访问和分享的一条内容，本站包含「项目」与「文章」两种类型
项目展示作品或案例的条目，强调职责、成果与技术栈
文章以文字为主的博客或笔记条目
草稿已写入仓库但未达到发布条件的内容条目，访客不可见
精选由站长显式指定在首页展示的条目
发布内容条目在线上站点可被公开访问的状态

02背景与目标

2.1 现状

个人介绍、项目作品与技术文章分别散落在简历文件、GitHub 仓库、社交平台和笔记工具中。访客需要跨多个平台跳转才能形成完整印象，站长也缺少一个统一、可控、可长期沉淀的展示位置。

2.2 问题

  • 没有单一入口能在 1 分钟内说明“我是谁、做过什么、如何联系”。
  • 作品与技术写作彼此割裂，无法互相导流。
  • 已有服务器方案需要付费与运维，与“长期低成本维护”的目标冲突。

2.3 产品目标

  1. 用一个免费托管的站点承接全部对外展示需求，站点源码与内容均可版本管理。
  2. 访客能在首页完成身份判断，并能到达任一项目详情、任一文章详情与联系方式。
  3. 站长发布新内容的动作不超过“写 Markdown + 提交仓库”，无需登录后台或操作服务器。
  4. 在无服务器成本的前提下，站点可稳定访问，内容量可平滑增长。

2.4 非目标

流量增长、商业转化、社区运营不在本次范围。

03用户与场景

3.1 用户

角色描述关注点期望完成动作
访客 · 招聘方通过简历或招聘平台进入站点方向匹配度、项目真实性、联系方式打开项目详情，获取联系方式
访客 · 技术同行通过文章分享链接进入站点文章质量、作者背景阅读文章，进入关于页或 GitHub
访客 · 潜在合作方通过社交平台进入站点能力范围、过往成果浏览项目，发起联系
站长站点所有者和唯一内容作者发布成本、可维护性、可控性新增或更新内容并发布上线

3.2 核心用户任务

主要用户
访客（招聘方、技术同行、潜在合作方）
触发
从简历、文章分享链接或社交平台点击进入站点
核心任务
在短时间内判断站长的能力方向是否匹配，并找到作品证据或联系方式
完成条件
访客到达联系方式，或已打开至少一个项目详情 / 文章详情
共享对象
内容条目（项目、文章），同时被访客消费、被站长维护

3.3 关键场景

S1 简历入口：招聘方点击简历中的站点链接 → 首页 30 秒内获取身份定位 → 点击精选项目 → 在项目详情看到技术栈与外部链接 → 通过关于页或页脚获取邮箱。

S2 文章入口：同行从分享链接直接进入文章详情（不经过首页）→ 读完文章 → 通过文末作者卡片进入关于页 → 浏览项目列表。

S3 内容发布：站长新建 Markdown 文件并填写 frontmatter 与正文 → 提交到仓库默认分支 → 自动构建发布 → 线上可访问，全程无需登录后台。

S4 内容纠错：站长发现文章有误 → 修改 Markdown → 再次提交 → 线上内容在 5 分钟内更新 Assumption, TBD。

05信息架构

5.1 页面结构

/
├── projects/              项目列表
│   └── {slug}/            项目详情
├── blog/                  文章列表
│   ├── page/{n}/          文章列表分页（P1 视内容量启用）
│   └── {slug}/            文章详情
├── about/                 关于与联系方式
└── 404                    无效地址页

5.2 全局导航

  • 顶栏从左到右：站点名称 / 头像（回首页）、项目、文章、关于、GitHub 外链（新窗口打开）。
  • 当前页面对应的导航项高亮。
  • 视口宽度小于 768px 时折叠为菜单按钮，展开后为纵向列表。
  • 导航在所有页面保持一致，不因页面层级变化增删项。

5.3 页脚

  • 版权信息，年份自动生成。
  • GitHub 主页链接。
  • 返回顶部入口。
  • RSS 入口（P1 启用后加入）。

5.4 URL 规则

  • 统一小写，使用短横线分隔单词。
  • 项目地址为 /projects/{slug}，文章地址为 /blog/{slug}。
  • slug 全站唯一，重名时构建失败并提示冲突文件名。
  • slug 一经发布不得修改；确需修改时，旧地址需 301 跳转到新地址（P1）。

06功能需求

F-01首页

目的：在首屏回答“我是谁”。

触发：访客打开站点根路径。

页面区块（自上而下）

  1. 身份区：姓名或昵称、一句话定位（不超过 40 字）、主行动入口「查看项目」与次行动入口「联系我」。
  2. 精选项目：最多 6 个，卡片展示封面、名称、一句话简介、技术标签。
  3. 最新文章：最多 5 篇，展示标题、发布日期、摘要。
  4. 页脚。

规则

  • 精选项目取 featured 为真且按 priority 降序排列，最多 6 个；不足 6 个时用最近更新的项目补足。
  • 全站项目数量为 0 时隐藏精选项目区块，不向访客展示空状态。
  • 最新文章按 date 降序排列，仅展示已发布条目。
  • 「联系我」跳转到关于页的联系方式区块。

边界：全站无任何内容时，首页仅展示身份区与页脚，主行动入口改为 GitHub 主页。

状态变化：无，纯展示页面。

F-02项目列表

触发：点击导航「项目」或直接访问 /projects。

内容：卡片列表，每张卡片包含封面、名称、一句话简介、技术标签、年份。

规则

  • 排序优先级：featured 降序 → priority 降序 → date 降序。
  • 草稿不出现在列表中。
  • 卡片整体可点击，进入对应项目详情。
  • 技术标签超过 3 个时仅展示前 3 个，其余折叠为「+N」。

边界：无公开项目时展示「暂无公开项目」空状态，并提供返回首页入口。

F-03项目详情

内容结构：标题、一句话简介、封面、项目概述、我的职责、技术栈、关键成果（可选，最多 3 条）、外部链接。

规则

  • 外部链接包含仓库地址与线上演示地址，至少提供其一 TBD；链接在新窗口打开并标注平台名称。
  • 正文使用 Markdown，支持图片、代码块、列表、引用。
  • 页面底部提供「上一个项目 / 下一个项目」导航，顺序与项目列表排序一致。
  • 项目正文中的图片需附带替代文本。

边界：草稿或不存在的 slug 返回 404；封面缺失时使用固定比例占位，保持列表与详情布局不塌陷。

F-04文章列表

内容：每页 10 篇 Assumption, TBD，条目标题、发布日期、摘要、预计阅读时长。

规则

  • 按 date 降序排列，草稿不可见。
  • 未填写摘要时截取正文前 80 个字符作为摘要 Assumption。
  • 文章总数超过 10 篇时启用分页，分页路径为 /blog/page/{n}。

边界：无已发布文章时展示空状态与返回首页入口。

F-05文章详情

内容结构：标题、发布日期与更新日期、标签（P1 起可点击）、正文、文末作者卡片、上一篇 / 下一篇导航。

规则

  • 正文支持代码高亮、表格、图片与引用。
  • 阅读时长按正文字符数除以 400（字/分钟）向上取整计算，最少 1 分钟 Assumption。
  • 未填写 updated 时不展示“更新于”。
  • 文末作者卡片包含姓名、一句话定位与关于页链接。
  • 上一篇 / 下一篇按发布时间相邻关系确定。

边界：slug 不存在时返回 404；正文图片缺失时显示替代文本，不破坏排版；正文内站内链接必须指向存在的页面，否则构建阶段给出警告 Assumption。

F-06关于页与联系方式

内容结构：个人简介（200–500 字）、技能与方向、经历时间线（可选）、联系方式。

规则

  • 邮箱默认以非明文形式展示，点击后复制到剪贴板并提示「已复制」 TBD 展示方式。
  • 社交链接以图标加文本形式呈现，至少包含 GitHub。
  • 不展示手机号、住址、身份证件等敏感信息。

边界：某类联系方式未填写时，该行整体不渲染，不出现空占位。

F-07导航、页脚与 404

  • 顶栏滚动时保持可见 Assumption。
  • 404 页包含提示文案、返回首页入口和最近 3 篇文章链接。
  • 所有页面的导航与主要链接均可通过键盘 Tab 键到达。

F-08响应式适配

  • 视口宽度 ≥ 1024px 为桌面布局，768–1023px 为平板布局，小于 768px 为单栏移动布局。
  • 移动端项目卡片单列展示，图片等比缩放，导航折叠为菜单。
  • 可点击元素触摸目标不小于 44×44px。
  • 视口宽度 320px 起不出现横向滚动条。

F-09SEO 与分享信息

  • 每个页面有唯一的 title 与 description。
  • 项目详情与文章详情输出 Open Graph 与 Twitter Card 元信息；分享图优先使用条目封面，缺失时使用站点默认图 TBD。
  • 生成 sitemap.xml 与 robots.txt，草稿不进入站点地图。
  • 使用语义化标题层级，单页仅一个一级标题。

F-10内容发布流程

触发：站长在仓库新增或修改内容文件，并提交到默认分支。

规则

  • 内容以 Markdown 加 frontmatter 定义，字段见第 7 章。
  • 提交后自动构建并发布，站长不需要访问服务器或登录任何后台。
  • 构建失败时线上保持上一成功版本，站长通过仓库通知得知失败 TBD 通知方式。
  • 发布成功的判定：访客可访问新地址，且页面内容与提交内容一致。

边界：frontmatter 缺少必填字段时构建失败，并明确指出文件名与缺失字段 Assumption；图片资源随内容一同提交到仓库，不依赖外部图床 TBD；单条内容正文超过 100KB 时提示拆分 Assumption。

07内容模型与字段

7.1 通用字段

字段类型必填规则
title文本是不超过 60 字，用于页面标题与列表展示
slug文本是小写字母、数字与短横线，全站唯一
summary文本是不超过 80 字，用于卡片与页面描述
date日期是首次发布日期，格式 YYYY-MM-DD
updated日期否最后实质修改日期，早于 date 时不展示
cover图片路径否建议 16:9，缺失时使用占位
tags文本数组否每个标签不超过 12 字
draft布尔否默认 false，为 true 时对访客完全不可见
featured布尔否仅项目使用，默认 false
priority数字否0–100，默认 0，数值越大越靠前

7.2 项目专有字段

字段类型必填规则
role文本是在项目中的职责，如“前端负责人”
stack文本数组是至少 1 项，用于列表页标签
repoUrl链接否代码仓库地址
demoUrl链接否线上演示地址，与仓库地址至少提供其一 TBD
highlights文本数组否关键成果，最多 3 条

7.3 文章专有字段

字段类型必填规则
readingTime数字派生由正文自动计算，作者不可手写
toc结构派生P1 启用，由正文标题自动生成

7.4 内容约束

  • 标签命名全站统一：同一含义只使用一种写法，不混用大小写与别名。
  • 封面只用于列表与分享图，不复用正文首图。
  • 删除条目时直接从仓库移除并发布，线上地址返回 404，不保留历史页面。
  • 草稿可以提交到仓库，但不进入任何列表、站点地图与搜索索引。

08角色与权限

角色可做不可做
访客浏览全部已发布内容、复制联系方式、跳转外部链接任何写操作
站长通过仓库提交新增、修改、删除内容—（无后台，无多用户协作）
P1 评论用户通过第三方评论服务发表评论修改文章正文
  • 站点不设权限分级与内容审核流程。
  • 所有内容变更以仓库提交记录为准，可追溯、可回滚。

09非功能需求

9.1 成本与托管约束

  • 现金成本为 0 元，使用 GitHub Pages 免费托管，仓库公开 Assumption。
  • 平台限制（以 GitHub 官方文档为准）：发布站点不超过 1GB，软带宽限制 100GB/月，软构建频率 10 次/小时。
  • 站点为纯静态产物，不依赖服务端运行时与数据库。

9.2 性能

  • 移动端 4G 网络下，首屏主要内容 3 秒内可读 Assumption。
  • 单个页面首屏所需的 HTML、样式与图片合计不超过 1MB Assumption。
  • 图片使用现代格式，并声明宽高以避免布局抖动。

9.3 可访问性

  • 正文文本与背景对比度不低于 4.5:1。
  • 所有内容图片提供替代文本，装饰图片使用空替代文本。
  • 全站可仅用键盘完成“首页 → 任意详情页 → 联系方式”的完整路径。

9.4 兼容性

  • 近两年发布的 Chrome、Edge、Safari、Firefox 正式版。
  • iOS Safari 与 Android Chrome 移动端。
  • 不要求兼容 IE。

9.5 可维护性与可迁移性

  • 所有内容以仓库内 Markdown 源码保存，可整体迁移到任意静态托管平台。
  • 页面样式与脚本不依赖外部 CDN 资源 Assumption。

9.6 隐私

  • 不采集访客个人信息，不接入需要登录的统计分析。
  • 页面不展示手机号、住址、身份证件等敏感信息。
  • 如启用统计，仅使用匿名、无 Cookie 方案 TBD。

10技术选型建议（附录）

说明：本章为明确要求的技术建议，供实现决策参考，不参与需求验收。

10.1 方案对比

维度AstroHugoHexo纯手写静态页
写作方式Markdown / MDXMarkdownMarkdown手写 HTML
模板灵活度高，组件化中，Go 模板中，EJS/Pug完全自由
构建速度中快中无构建
依赖与维护Node 工具链单一可执行文件Node 工具链无依赖
适合场景作品集 + 博客，需要定制内容量大、追求极简运维中文生态与主题丰富极简单页

10.2 推荐

首选 Astro：内容集合天然适合“项目 + 文章”两类内容，Markdown/MDX 写作，组件化便于实现项目详情等定制版式，构建产物为纯静态文件，官方提供 GitHub Pages 部署说明。

次选 Hugo：不依赖 Node、构建速度快、运维负担最低，代价是模板需要学习 Go template 语法。

不建议首个版本手写纯静态页：一旦内容超过 10 条，列表、分页、SEO 元信息都需要重复手工维护。

10.3 免费托管与发布方式

  • 用户站点：仓库命名为 {username}.github.io，访问地址为 https://{username}.github.io。
  • 项目站点：任意仓库名，访问地址为 https://{username}.github.io/{repo}。
  • 自定义域名：在仓库设置中绑定域名，DNS 添加 CNAME 指向 {username}.github.io，GitHub Pages 提供免费 HTTPS TBD。
  • 发布链路：本地编写内容 → 提交并推送到默认分支 → 自动构建 → Pages 发布。
  • 该流程满足第 6 章 F-10 对“无需后台、无需服务器”的要求。
