## 为什么还做 Servlet

在学完 Spring Boot 之后，我回头用 Servlet + JSP 写了一个电商系统。原因很简单：我想知道不用框架时，一个请求到底发生了什么。

这个项目没有自动配置，没有依赖注入，也没有现成的分页插件。每个环节都要自己接起来。

## MVC 在代码里长什么样

项目按控制器、数据访问、实体与视图分层：

```text
Servlet Controller → DAO → MySQL
        ↓
   JSP + JSTL 渲染
```

控制器只负责接收参数、调用业务和选择视图；DAO 负责 SQL 与实体映射；JSP 只做展示。

分层的好处不是“看起来规范”，而是修改某一层时，其他层不用跟着改。比如换表结构，只需要调整 DAO。

## 设计模式不是背出来的

项目里用了三种模式：

- **DAO 工厂**：统一创建数据访问对象
- **代理模式**：封装数据库连接的获取与关闭
- **过滤器**：拦截会员端与管理端请求，做登录与权限校验

写的时候才发现，这些模式解决的都是具体问题：不想让业务代码重复处理连接，不想让控制器依赖具体实现，不想在每个页面里判断登录状态。

## 安全意识是被逼出来的

没有框架帮忙，很多细节必须自己处理：

- 密码用 SHA-256 加盐存储
- 登录态放在 HttpSession
- 管理端与会员端使用独立过滤器
- 未登录请求直接跳转，而不是只隐藏按钮

这些做法并不完美，但让我理解了“权限控制”必须发生在服务端。

## 回到 Spring

做完这个项目，再使用 Spring Boot，视角发生了变化：自动配置、拦截器、事务管理、视图解析，这些“黑盒”都能对应到具体环节。

框架不是魔法，它只是把重复工作封装起来。理解封装之前的样子，遇到问题时才更容易定位。

## 适合谁

如果你已经能用框架完成项目，但说不清请求链路，我建议花两周手写一个小型 Servlet 项目。它不会让简历更亮眼，但会让基础更结实。
