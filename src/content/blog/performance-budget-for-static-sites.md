## 分数不是目标

用评测工具跑出一个高分并不难，难的是在内容增加、需求变化之后仍然保持。分数是结果，预算才是约束。

性能预算应该回答三个问题：

- 哪些资源是首屏必须的
- 每类资源的体积上限是多少
- 超出预算时，先删什么

## 给这个站点定的预算

这是一个以文字为主的站点，预算可以定得很紧：

| 项目 | 预算 |
| --- | --- |
| 首屏 HTML + CSS | 80KB |
| 首屏 JS | 10KB |
| 首屏图片 | 300KB |
| 字体文件 | 0（使用系统字体） |
| 首屏可读时间（4G） | 3 秒内 |

真正限制设计的是 JavaScript 那一行。零客户端脚本意味着导航、列表与文章都不需要等待水合，交互增强只能作为可选项存在。

## 预算如何被执行

预算如果不进入流程，就只是一段文字。我的做法是：

1. 在构建后检查产物清单，超限时输出警告
2. 图片在提交前压缩，并声明宽高
3. 新依赖必须说明它带来的体积
4. 每季度重新跑一次移动端测量

这些检查不需要复杂工具，一个脚本加上几条约定就足够。

## 什么时候可以超预算

预算不是绝对的。当新增内容能明显提升阅读体验时，可以超，但要同时决定拿什么来换。

例如给文章加代码高亮，会让样式体积增加。换来的结果是代码更易读，这笔交易值得；而为了一个装饰性动画引入整个动画库，就不值得。

## 把取舍写下来

性能讨论最容易变成感觉之争。把预算写进文档，把每次例外记录下来，下一次就不需要重新争论一遍。

这也是这个站点坚持写工程笔记的原因：决定本身会过时，但做决定的理由值得保留。
