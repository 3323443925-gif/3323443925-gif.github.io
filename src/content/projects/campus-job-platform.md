## 背景

校园招聘的日常流程通常散落在表格、群聊和线下沟通里：学生找岗位，HR 收简历，教师审核企业，管理员做统计。信息在不同角色之间反复转发，状态很难追踪。

这个项目把这些环节放进同一套系统，覆盖从岗位发布、简历投递、面试安排到就业统计的完整流程。

## 四类角色

| 角色 | 主要动作 |
| --- | --- |
| 学生 | 维护简历、浏览岗位、投递、查看面试通知 |
| HR | 企业认证、发布岗位、查看简历、发起面试 |
| 教师 | 审核企业入驻与岗位、查看学生投递情况 |
| 管理员 | 用户与专业管理、企业审核、就业数据统计 |

角色不同，看到的菜单和可调用的接口也不同。权限不是前端隐藏按钮，而是在后端通过 JWT 与拦截器统一校验。

## 系统结构

- 后端：Spring Boot 3.5 + MyBatis + MySQL
- 前端：Vue 3 + Element Plus + ECharts + Vite
- 认证：JWT Token + 请求拦截器
- 文件：阿里云 OSS 存储简历与附件
- AI：Spring AI 接入 DeepSeek API

工程采用 Maven 多模块拆分：`pojo` 放实体，`utils` 放通用工具，`end-project` 承载控制器、服务与数据访问。这样依赖版本和公共代码只维护一份。

## AI 能力落在哪里

我没有把大模型做成一个通用聊天框，而是限制在三个具体场景：

1. **简历分析**：解析简历文本，输出结构化字段与改进建议。
2. **简历筛选**：根据岗位要求给出匹配度参考，帮助 HR 排序。
3. **AI 面试**：按岗位生成问题，记录候选人的回答。

所有 AI 结果都作为建议展示，最终决定仍然由人完成。模型输出使用结构化格式并做校验，解析失败时回退到普通文本，不阻塞主流程。

## 权限与状态如何落地

- JWT 中携带用户标识与角色，拦截器统一校验，不依赖前端隐藏按钮
- 学生、HR、教师、管理员看到不同菜单，接口权限在后端判断
- 企业认证、岗位审核、投递与面试按状态推进，避免一个字段承担多种含义

## 难点与取舍

**权限与状态**：四类角色交叉，投递、面试、录用又是多段状态。先把角色与状态画清楚，再写接口，比边写边加字段更省事。

**AI 的不确定性**：同一个简历可能得到不同的分析结果。我的处理是把 AI 放在流程的辅助位置，不参与权限判断，也不直接写数据库。

**前后端联调**：接口先定字段与错误码，再并行开发页面，能减少大量返工。
